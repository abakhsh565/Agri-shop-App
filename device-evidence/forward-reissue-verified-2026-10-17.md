# The forward re-issue of 0177–0198 — what it is, and what was measured

**When:** 2026-10-17. **Engines:** PGlite (in-process) and a real Supabase CLI stack, Postgres **17.6**.
**Production was not contacted.** No production row was read or changed, and nothing was applied to it.

## 1. What was produced

Six files numbered after `0208`, generated by `scripts/dev/reissue-forward-files.mjs` from the range's
own statements — the generator re-expresses each file's *intent*; it does not copy SQL:

| File | Statements | Sources |
|---|---|---|
| `0209_the_objects_no_tracked_file_creates.sql` | 25 | 19 columns + `delete_branch` + `my_shop_ids` (0168, 0191) |
| `0210_the_marketplace_chain_at_the_state_it_ends_in.sql` | 20 | 0184, 0185, 0186, 0187 — final state only |
| `0211_a_branch_is_its_own_identity.sql` | 19 | 0183, 0188 (functions), 0191, 0196 |

## 2. The measurements

```
PGlite, production's baseline   19 files  445 statements  0 sql failures  0 env-gap
PGlite, staging's baseline      16 files  429 statements  0 sql failures  1 expected-phase baseline stmt
real PG 17.6, production base   19 files  445 statements  0 sql failures  AGREES with PGlite (per file)
real PG 17.6, staging's base    16 files  429 statements  0 sql failures  AGREES with PGlite (per file)
intent probe, production base   20/20 checks held
intent probe, staging base      20/20 checks held
```

The staging runs apply the 16 files QA's ledger lacks (`0199`–`0214`) onto the already-populated staging
schema. Both baselines' artifacts carry no `GRANT`, so the harness installs hosted Supabase's default
privileges **before** the objects exist — the only order in which a migration's `REVOKE` can mean
anything, and the same mapping `scripts/dev/local-db.mjs` applies to the local database.

The one staging baseline failure is the artifact's own: `_test_check_auth()` sits at the head of the
dump, marked `-- @phase: functions-pre-tables`, and cannot compile there (`function app_is_admin() does
not exist` — `app_is_admin` is defined further down the same artifact). It is counted and printed, not
swallowed, and it is not caused by — or touched by — this batch. The rehearsal now classes
`-- @phase:` failures the same way the PGlite verifier does (`expectedPhaseAfterRetry` vs
`unexpectedAfterRetry`), so this artifact defect no longer reads as a failure of the selection, and an
unexpected baseline failure still fails the run.

## 3. Measuring the result, not the failure count

A guarded statement that declines to run reports no failure, so a clean apply is a floor. The probe
(`scripts/dev/probe-rehearsal-intent.mjs`) reads `pg_catalog` and the privilege tables after the batch
and asserts:

* the marketplace view exists and `anon` can read it; `shops.marketplace_radius_km` is absent;
  `search_marketplace` and `set_marketplace_settings` keep the shapes `0187` ended with;
* `audit_events` has no permissive INSERT policy, its client write policy says `false`, every SELECT
  policy carries a shop predicate, and the snapshot trigger is on all three financial tables;
* the permission gate is restrictive on ten tables; **all seven** branch-read policies are restrictive;
* `anon` and `authenticated` hold no write privilege on the seven financial tables, while
  `authenticated` can still read `sales`, `products`, `customers` and `companies`;
* no guard, helper or trigger function the batch creates is executable by `anon` (or, for triggers, by
  any client role);
* the membership substrate exists, `process_return` is the renamed `payload jsonb` shape, and the 29
  named RPCs are present.

## 4. Four defects the probe found (all fixed in the generator)

1. **Guarding a create on its own existence** — `marketplace_listings` was never created on production,
   and two `comment on` guards resolved their subject to `public`. Guards now name the *dependency*.
2. **`CONTINUE` outside a loop** — 0192's patch block refused the whole file on the real engine.
3. **Two files defining one policy** — 0188's sweep and 0180's permissive rewrite of
   `stock_adjustments_branch_select` split across files; the higher version won, so six of seven
   branch-read policies were restrictive. The sweep is now the last statement of the file that rewrites
   the policies, and the generator refuses to emit one object from two files.
4. **A REVOKE a later CREATE undid** — `my_shop_ids` (created by 0209 on a schema that never had it) and
   `audit_operational_snapshot` arrived with PostgreSQL's default `PUBLIC EXECUTE`. Every ledger ACL
   statement is now applied a second time at the end of `0214`, and trigger functions are closed to
   every role. This narrows access; nothing is granted.

Two smaller ones were fixed on the way: a trigger drop guarded on `relname = 'undefined'` (the table was
never read out of the statement), and a guard note containing a newline, which became SQL on the real
engine (`syntax error at or near "default"`) while the generator reported success — the emission now
refuses a multi-line note.

A sixth was found only on the live schema (see §7): 0180's assertion counted 0195's restrictive
permission gates as if they were tenant-blind. It now asks only permissive policies.

## 5. What this does NOT establish

* **Production's ACLs have not been measured.** The batch's own revokes and grants are asserted; the
  privileges production already holds are not observable from a baseline artifact that carries none.
* **Nothing has been applied to production.** These are rehearsals against frozen baselines.
* A production apply still needs a **fresh restore-verified backup** taken immediately before it; the
  earlier backup is outside its one-hour gate.
* Production cleanup remains a separate owner decision.

## 6. How to reproduce

```bash
FILES=$(ls supabase/migrations/*.sql | awk -F/ '{print $NF}' \
  | grep -E '^(0179|0181|0190|0199|020[0-9]|021[0-4])_' | sed 's#^#supabase/migrations/#' | paste -sd, -)

node scripts/verify-forward-on-baseline.mjs --baseline production --files "$FILES" \
  --json backups/baseline-prod-full-batch-verified.json

node scripts/dev/rehearse-on-local-engine.mjs --baseline production --files "$FILES" \
  --compare-report backups/baseline-prod-full-batch-verified.json \
  --json backups/rehearsal-prod-full-batch.json --keep

node scripts/dev/probe-rehearsal-intent.mjs --db rehearsal_production \
  --json backups/probe-rehearsal-production.json
```

The QA lane swaps `production` for `staging` and selects `0199`–`0214`; its reports are
`backups/baseline-staging-qa-lane-verified.json`, `backups/rehearsal-staging-qa-lane.json`.

Supporting checks: `npx tsc --noEmit` (exit 0), `npx vitest run tests/unit` (75 files, 987 tests), and
`node scripts/dev/reissue-forward-files.mjs --check` (the emitted files are byte-identical to what the
generator produces).

## 7. Applied to hosted QA, 2026-10-17

`node scripts/migrate.mjs apply --env staging --apply` — six files, each one transaction together with
its ledger rows:

```

✓ 0210 (20, recorded)             ✓ 0213 (44, recorded)
✓ 0211 (19, recorded)             ✓ 0214 (23, recorded)
```

**The first attempt failed, and that is the most useful result of the day.** 0209–0211 applied; then
`0212` failed and rolled back with `0180 left a tenant-blind policy in place:
stock_adjustments.permission_insert_gate, stock_adjustments.permission_read_gate`. Those are 0195's
**restrictive** permission gates, which hosted QA already carries and neither frozen baseline does — a
restrictive policy only narrows, so an assertion about "a policy that mentions neither the shop nor a
parent row's shop" has to be asked of permissive policies. The re-issued assertion now filters on
`p.polpermissive`; the file applied on the retry, and both baselines were re-verified afterwards with
the same 445/429 statements and zero failures.

Ledger: **206 files, 206 rows, every hash matches — `VERIFY: PASS`.**
