## The 14 integration failures — root causes

Verified per file. The decisive structural fact: **none of the six files imports anything from
`src/`.** Their complete import lists are `vitest` plus `../setup/qa-client`. Phase 1 changed
`envGuard`, `environmentContract`, `supabase.ts`, `authMode` and `auth.ts` — none of which is
reachable from these tests, which talk to the database through `pg` and HTTP helpers.

| # | File | Failing tests | Category | Root cause |
|---|---|---|---|---|
| A | `splitPayments.test.ts` | 8 | test harness | `error: NOT_AUTHENTICATED` raised by the database during setup |
| A | `employeeAccessOverrides.test.ts` | 3 | test harness | same: the override write never lands, so the read returns role defaults |
| A | `rbacEnforcement.test.ts` | 1 | test harness | same |
| A | `rbacFoundation.test.ts` | 1 | test harness | same |
| B | `priceTraceability.test.ts` | whole file (7 skipped) | DB contract drift | `create_product: INVALID_UNIT: a product is measured in kg or liter, not "piece"` |
| C | `tenantResolverReplay.test.ts` | 1 | stale expected snapshot | the DB has 3 functions the test's locked list omits |

**13 + 1 = 14. The tally reconciles exactly.**

**Root cause A — the harness cannot establish `request.jwt.claims` (13 failures).** DB-verified, not
inferred. The deployed `app_current_user_id()` is:

```sql
SELECT NULLIF(NULLIF(current_setting('request.jwt.claims', true), '')::json->>'sub', '')::uuid;
```

When the harness has not set those claims this returns `NULL`, the RPCs reject with
`NOT_AUTHENTICATED`, the write never happens, and every downstream assertion then fails on missing
rows — which is exactly the assertion pattern observed. Corroboration: `user_permissions` holds
**0 rows** even though the overrides test writes to it, and `get_effective_permissions` *does*
reference `user_permissions`/`is_override` (2,897-char definition read from the catalog), so the
resolver is not the problem — the write never reaches it.

**Root cause B — the deployed RPC's contract moved past the test.** Verified from the catalog: the
deployed `create_product` definition contains the literal `INVALID_UNIT: a product is measured i…`
rule. The test sends `piece`; the function requires `kg` or `liter`. The database rejects it before
the test's own assertions run, which is why the whole suite fails in `beforeAll`.

**Root cause C — the test asserts a snapshot the database has grown past.** `authorize_business_action`,
`get_effective_permissions` and `resolve_invite` **all exist** in `public` (verified by catalog
query). The test's expected list predates them. A "replay" test that pins a function list will fail
every time a function is added; that is the test design, not a regression.

**Can Phase 1 affect any of them? No, and here is the proof:**

1. **No import path.** All six files import only `vitest` and `../setup/qa-client`. The modules Phase 1 changed are not in their dependency graph.
2. **No config path.** Every failure is a database answer (`NOT_AUTHENTICATED`, `INVALID_UNIT`) or an assertion about database state. Phase 1 cannot produce either — it changed only environment resolution, the client constructor and the OTP decision.
3. **Negative control.** The full run was grepped for every signature Phase 1 can emit — `EnvironmentConfigurationError`, `ENVIRONMENT MISMATCH`, `[CONFIG]`, `DEMO_OTP`, `VITE_APP_ENV`, `EnvGuard] Refusing`, `assertDemoOtpAllowed`, `demoCodeAccepted`. **Zero occurrences.**
4. **No schema changes.** No SQL file changed (`git status`: no modified `.sql`). And the DB-side causes are verified directly in the deployed functions.
5. **Identical in isolation.** `splitPayments` and `employeeAccessOverrides` were also run alone and produced the same failures, so this is not cross-test interference.
