# FEATURE-MAP.md — MVP feature registry, dependency map and change-impact workflow

This is the Engineering OS answer to one question:

> **What exists, what depends on it, what could be affected by a change, and what evidence shows
> the affected behaviour is still safe?**

It is deliberately small. It registers meaningful product capabilities (not every button), points
at the authoritative code/tests/evidence instead of copying them, and is enforced by a guard so it
cannot rot silently.

| Question | Authority (do not re-derive) |
|---|---|
| Which screen exists, where is it, which lanes cover it | `SCREEN-INDEX.md` (generated by `node scripts/dev/index.mjs`) |
| Which tables / RPCs / stores a file uses | `dependency_graph.json` (generated by `scripts/scan-frontend-deps.cjs`) |
| Which E2E lane covers which files | `scripts/dev/lane-map.json` |
| Which DB objects a table/RPC change impacts | migrations `0077_impact_intelligence.sql`, `0078_frontend_impact_intelligence.sql` (`analyze_table_impact`, `analyze_function_impact`, `load_dependency_graph`) |
| What was verified, on what, with which log | `PHASE_2_BROWSER_SAFETY.md` §17 (+ addendum) and `backups/` logs |
| Current machine state, tiers, last green run | `ENGINEERING_OS_STATE.md` (checkpoint block) + `npm run resume` |
| The registry itself | `feature-registry.json` (machine-readable) + this file (narrative/workflow) |

Guard: `tests/unit/featureRegistryGuard.test.ts` — fails when this file or the registry drifts
from reality (missing fields, unknown screens/permissions/tests, unknown dependency ids,
non-symmetric reverse dependencies, a missing workflow section). Run `npx vitest run
tests/unit/featureRegistryGuard.test.ts`.

## B. Dependency map

Feature → UI → State → Permission → RPC/API → Database → Related features → Tests. The edge list
is data in `feature-registry.json` (`dependsOn` / `dependedBy`, kept symmetric by the guard); the
file→table/RPC/store links are data in `dependency_graph.json`. Worked chains:

```text
Split payment:  sale/cart (UI)
              → cartStore + salesStore (State)
              → sales.view (Permission)
              → create_sale (RPC)
              → sales, sale_items, sale_submissions (DB)
              → void-sale, returns, reports, dashboard, assistant (Related)
              → splitPayment lane, saleIdempotency, splitPayments (Tests)

Customer payment: customers/:id/record-payment (UI)
              → customersStore (State) → customers.view (Permission)
              → record_customer_payment (RPC) → customers, customer_payments (DB)
              → customer balance → credit sale → credit limit → reminders → dashboard/reports

Stock threshold: settings + products (UI) → stockAlerts (Lib) → settings.view/alerts.view
              → get/set_stock_alert_settings (RPC) → app_settings, products (DB)
              → dashboard action center, notifications (Related)
              → stockAlerts.test, appSettingsIsolation, shopScopedPolicyGuard (Tests)
```

**Reverse dependencies are the point.** “What depends on this?” is answered by `dependedBy` in
the registry for feature-level work, by `dependency_graph.json` for file/table-level work, and by
`analyze_table_impact` / `analyze_function_impact` in the database for schema-level work.

## C. Change-impact analysis (permanent, 13 steps)

Before modifying an existing feature:

```text
1. Identify the feature being changed.
2. Identify its direct dependencies.
3. Identify the features, screens, and business rules that depend on it.
4. Identify affected database tables, RPCs, and APIs.
5. Identify affected permissions and security boundaries.
6. Identify affected EN/LTR and UR/RTL surfaces.
7. Identify affected tests and evidence.
8. Determine which existing evidence remains valid.
9. Invalidate only the evidence genuinely affected by the change.
10. Implement the change.
11. Run targeted verification.
12. Run regression for the affected dependencies.
13. Update the feature, dependency, and evidence records.
```

Do not rerun the entire application for every small change. Use dependency-aware verification
(`npm run verify:plan` → computed tier + affected lanes + REUSE decisions, then `npm run verify`)
while preserving the required regression coverage for material risk. Some changes are small but
unavoidably wide: any edit under `src/**` mechanically invalidates `crossScreenSync` plus the two
unmapped specs, and any edit to `src/lib/i18n.ts` invalidates every lane whose globs name it.
That is the engine being conservative about *files*, not a demand for the full suite.

## D. Evidence registry

Statuses (one vocabulary for the whole Engineering OS):

| Status | Meaning | In this repo today |
|---|---|---|
| **VALID** | Behaviour, context and dependencies unchanged since it was captured | most rows in `PHASE_2_BROWSER_SAFETY.md` §17 |
| **INVALIDATED** | A change touched what the evidence covers; rerun before promotion | lanes whose globbed files changed |
| **REPLACED** | Superseded by a newer run/decision (keep the pointer, not the claim) | earlier gate logs superseded by later green runs |
| **FIXED + REVERIFIED** | A real defect was fixed and re-proven | 0181 audit_events, 0182 app_settings |
| **NOT APPLICABLE** | The check does not exercise this feature/environment | native-biometric checks in browser lanes |
| **BLOCKED** | Cannot be verified now; reason recorded | none open |

Recorded per meaningful workflow: test/workflow, environment (QA `bpybjrjenwccowvtrevu`; production
never used for verification), role, tenant/branch, browser/device, result, evidence location,
date/version/commit, what it proves, and whether it is still valid. The narrative matrix is
`PHASE_2_BROWSER_SAFETY.md` §17 (+ addendum); raw logs are `backups/*.log` (gitignored, cited by
name); per-feature evidence pointers are in `feature-registry.json`.

**NO ACTUAL EVIDENCE = NO PASS = NO ADVANCEMENT.** A document, a rendered screen or a compiled
file is not evidence that behaviour is correct.

## E. Evidence reuse and invalidation

Reuse evidence (do not rerun merely because a new task started) when all hold: the tested
behaviour is unchanged; the relevant implementation is unchanged; its dependencies are unchanged;
environment and context still apply; and the evidence is still trustworthy.

Reconsider or rerun when the change affects any of: implementation · a dependency · business
rules · database schema · RPC/API behaviour · permissions or security · tenant/branch behaviour ·
state management · shared components · language or internationalisation · RTL/LTR · browser- or
device-sensitive behaviour · the original failure mode · any other material risk.

`scripts/dev/verify.mjs` implements the mechanical half (globs + byte-identical check + tier), and
`backups/gap-check.mjs` reports REUSE/RERUN per lane from the same data. The human half — deciding
that a comment-only or copy-only change leaves behaviour evidence valid — is a recorded decision
in the evidence log, never a silent skip.

## F. Future feature development rule

Every new feature and every meaningful modification enters the workflow automatically:

```text
new or modified feature → dependency analysis → implementation →
targeted verification → affected regression → evidence update
```

Nobody has to be reminded to “check what this change might break” — this section plus
`AGENTS.md` §8 make it a standing requirement, and the guard keeps the records honest.

Every user-facing change is checked in **EN + LTR** and **UR + RTL** through the centralized
language/design system (`src/lib/i18n.ts`, `useT()`, logical properties, `ps-*`/`pe-*`,
`text-start`/`text-end`). No per-feature translation implementation.

## G. Where everything lives (source of truth)

1. **What the product contains** — §A above + `feature-registry.json`.
2. **Modules and features** — §A; screens via `SCREEN-INDEX.md`.
3. **Dependencies** — §B + `feature-registry.json` + `dependency_graph.json` + DB impact RPCs (0077/0078).
4. **Critical business rules** — `feature-registry.json` `rules` + the locked guards in `tests/unit/` (money, overdueCredit, reminderEscalation, signalEngine/suppression, reentrancyGuard).
5. **Security boundaries** — §A security rows + `tests/integration/tenantBoundarySweep.test.ts`, `shopScopedPolicyGuard.test.ts`, `auditIntegrity.test.ts`, `appSettingsIsolation.test.ts`; RLS lives in `supabase/migrations/`.
6. **Where the implementation lives** — `src/`, five shells: `src/router/index.tsx` is the route authority.
7. **Where the tests live** — `tests/unit/` (guards), `tests/integration/` (QA database), `tests/e2e/` (Playwright lanes), lane map `scripts/dev/lane-map.json`.
8. **Where the evidence lives** — `PHASE_2_BROWSER_SAFETY.md` §17 + `backups/*.log` + this file’s registry.
9. **How to do change-impact analysis** — §C; start with `npm run resume`, then `npm run verify:plan`.
10. **How evidence reuse/invalidation works** — §D, §E.
11. **How staging and production release work** — `environments.json` is the only environment→project map (staging/QA `bpybjrjenwccowvtrevu`; production `gkswcfljxlutkfdvvqng` is never used for verification). Migrations apply forward-only via `node scripts/migrate.mjs apply --env staging --apply`, verified with `npm run migrate:verify` + baseline/ledger checks. Android release exists only through `.github/workflows/build-apk.yml`; a release is never implied by a local build. **No production action without explicit authorization.**

## H. MVP scope protection

Small, durable, understandable, maintainable. No microservices, no extra infrastructure, no
enterprise internal platform, no feature-flag system, no dashboards or automation beyond the
scripts named here. New mechanisms require evidence that the current MVP genuinely needs them.
